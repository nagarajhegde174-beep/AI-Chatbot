# SERVICE_CONTRACTS.md — Service Contracts

The explicit, versioned agreements between NexaAI services.

**Status: specified, not implemented.** Every contract here is a commitment that Phase 1 and
later must honour. A change to any contract in this document updates this document in the same
change ([`RULES.md`](RULES.md) §12).

Related: [`ARCHITECTURE.md`](ARCHITECTURE.md) for the system,
[`ARCHITECTURE.md`](ARCHITECTURE.md) §13 for why the boundaries are where they are.

---

## 1. General conventions

### 1.1 URL spaces

| Space | Audience | Path |
|---|---|---|
| Public | Browser, via the gateway only | `/api/v1/**` |
| Inter-service | Service to service, never from the internet | `/internal/v1/**` |
| Operational | Infrastructure only | `/actuator/**` |

**Rules.**
- The browser never calls a service port. Only the gateway is public.
- `/internal/**` and `/actuator/**` are denied at the edge **and** by the gateway. Two
  independent locks, because one configuration mistake should not expose internals.
- Every path is versioned. Breaking changes mean a new version, never an in-place change.

### 1.2 Headers

| Header | Direction | Purpose |
|---|---|---|
| `Authorization: Bearer <token>` | client → service | Access token. The only accepted credential. |
| `X-Correlation-Id` | everywhere | Generated by the gateway if absent; propagated on every hop; returned to the client |
| `X-Request-Id` | client → service | Optional client-supplied id, adopted as the correlation id if well-formed |
| `Accept-Language` | client → service | Reserved for Phase 10 localisation. Not used in Phase 1 |

### 1.3 Status codes

| Code | Meaning here |
|---|---|
| 200 / 201 / 204 | Success. 201 carries a `Location` on creation. |
| 400 | Malformed request. The message names the field. |
| 401 | Missing, invalid, expired or revoked token. Never a hint about which. |
| 403 | Authenticated but not permitted. **Reserved for ADMIN**, to avoid leaking existence. |
| 404 | Does not exist, **or** exists but is not yours. Deliberately ambiguous. |
| 409 | Conflict, e.g. email already registered. |
| 422 | Semantically invalid, e.g. a password failing policy. |
| 429 | Rate limited. Always with `Retry-After`. |
| 502 / 504 | An upstream service failed or timed out. |
| 503 | Deliberately unavailable. Circuit breaker open. |

**403 versus 404.** A `USER` asking for another user's resource gets 404 whether or not it
exists. 403 confirms it exists, which is an enumeration channel
([`SECURITY.md`](SECURITY.md) §4.2).

### 1.4 Error envelope

Every service, identically shaped:

```json
{
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "Email or password is incorrect.",
    "correlationId": "0f9c1e2a-4b7d-4f1e-9a3c-2d5e6f708192",
    "timestamp": "2026-01-15T10:30:00Z",
    "details": null
  }
}
```

Rules:
- `code` is a stable machine-readable identifier, UPPER_SNAKE_CASE. Clients branch on it.
- `message` is human-readable, safe to display, and **never** a stack trace, a SQL message or a
  provider's raw error.
- `correlationId` is always present, so a user can report a real problem.
- `details` carries field-level validation errors only, and never echoes a submitted secret:
  `{"email": "must be a valid address"}`.

### 1.5 Pagination

Request: `?page=0&size=20`, `size` capped at 100.

```json
{
  "content": [],
  "page": 0,
  "size": 20,
  "totalElements": 137,
  "totalPages": 7,
  "last": false
}
```

Never offset pagination on a large table. If a table can grow without bound, keyset pagination
is used and this shape does not apply.

### 1.6 Timestamps and identifiers

- **Timestamps:** ISO-8601 UTC with an offset, `2026-01-15T10:30:00Z`. Never a local time, never
  a bare timestamp.
- **Identifiers:** UUID v4 in API payloads. Exposed as `string` and treated as opaque by
  clients. Internal primary keys are their own concern and never appear in a contract.
- **Enum values:** UPPER_SNAKE_CASE.

### 1.7 Idempotency

`POST` that creates something accepts `Idempotency-Key`. The same key replays the original
response instead of creating a duplicate. Scoped per caller, with a defined retention window.

## 2. Boundary endpoint

Every service implements this. It exists so a boundary violation is **visible** rather than
assumed, and it is what a Phase 0 rule check or an operator can assert.

### `GET /internal/v1/{service}/info`

```json
{
  "service": "auth-service",
  "version": "0.1.0",
  "role": "Credentials, tokens, account status",
  "port": 8081,
  "database": "nexa_auth",
  "listensKafka": true,
  "consumes": ["none"],
  "produces": ["auth.user.registered.v1"]
}
```

`database` is `null` for `api-gateway` and `ai-service`. That field is the boundary assertion:
a service that owns a database must name exactly one, and it must be its own.

**Not implemented in Phase 0** ([`ARCHITECTURE.md`](ARCHITECTURE.md) §13, decision 015). It ships with each
service, in that service's own phase.

## 3. DTO boundaries

### 3.1 DTOs are duplicated deliberately

Two services exchanging a payload do **not** share a type. Each declares its own, shaped to its
own need. [`ARCHITECTURE.md`](ARCHITECTURE.md) §13, decision 013, explains why.

### 3.2 Entity types never cross a boundary

A JPA entity, a database row and an API payload are three different things. What crosses is a
DTO.

| Never crosses | Why |
|---|---|
| JPA entity | Leaks the schema, and forces lazy-loading decisions onto the caller |
| Database row | Same |
| Internal enum with ordinal values | Ordinals change when someone reorders them |
| Internal exception | Leaks implementation detail |

### 3.3 Enumerations shared across services

These string values are part of a contract and must not be renamed:

| Enum | Values | Owner |
|---|---|---|
| Role | `USER`, `ADMIN` | auth-service |
| Account status | `ACTIVE`, `SUSPENDED`, `DEACTIVATED` | auth-service |
| Document status | `UPLOADING`, `PROCESSING`, `READY`, `FAILED` | document-service |
| Subscription status | `ACTIVE`, `PAST_DUE`, `CANCELLED`, `EXPIRED` | subscription-service |
| Plan interval | `MONTHLY`, `YEARLY` | subscription-service |
| Model provider | `OPENAI`, `GEMINI`, `GROQ` | ai-service |
| Citation type | `DOCUMENT` | chat-service |

**Adding a value is a compatible change.** Renaming or removing one is not; it requires a new
version.

### 3.4 Sensitive fields never cross a boundary

| Field | Rule |
|---|---|
| Password hash | Never leaves auth-service, in any DTO, ever |
| Refresh token | Never returned. Only the token *value* is issued, and only at issue time |
| API keys, key secrets, webhook secret | Never in any response, including admin endpoints |
| `jti` of another user's token | Never in any response |
| Prompt content in analytics | Never. Analytics carries counts, not content |

## 4. API Gateway

Port 8080. Owns no database.

### 4.1 Responsibilities

**Implemented in Phase 2:**

- Verify the access token (RS256), rejecting invalid requests before routing.
- Route by path prefix to the owning service.
- **Strip client-supplied identity headers, then set verified ones** (`X-User-Id`,
  `X-User-Email`, `X-User-Roles`).
- Remove the bearer token before forwarding, so no upstream holds a replayable credential.
- Generate and propagate `X-Correlation-Id`, accepting an inbound value only if it is a UUID.
- Apply CORS from a configured allowlist, refusing to start when the list is empty.
- Return JSON errors in the same envelope the services use.

**Not implemented.** Listed so this contract is not read as a claim:

- Rate limits
- Request body size limits
- Circuit breaking
- `/.well-known/jwks.json` and `GET /internal/v1/gateway/info`
**The gateway holds no business logic.** A route that computes something belongs in the service
that owns the data.

### 4.2 Route table

Implemented routes only. A route is added when its service exists, not in anticipation: a
configured route pointing at a service that is not running fails at request time and reads like
a broken service.

| Public path prefix | Rewritten to | Target | Phase |
|---|---|---|:--:|
| `/api/auth/**` | `/api/v1/auth/**` | `auth-service:8081` | 2 |
| `/api/users/**` | `/api/v1/**` | `user-service:8082` | 2 |
| `/api/chat/**` | `/api/v1/**` | `chat-service:8083` | 3 |

So `/api/users/me` goes to user-service `/api/v1/me`, and `/api/users/admin/users` goes to
`/api/v1/admin/users`.

**`RewritePath`, not `StripPrefix`.** `StripPrefix=1` on `/api/auth/login` yields `/auth/login`,
which Auth Service does not serve; it answers on `/api/v1/auth/**`. Stripping a segment only works
when what remains happens to match, which is not a property to rely on.

**Not routed:** every other service prefix, and Auth Service's `/internal/v1/auth/**`. The
internal surface is service-to-service and must not be reachable from the public edge.

### 4.3 Per-route policy

| Policy | Value |
|---|---|
| Authentication | Required except the configured public paths |
| Body size | Not implemented |
| Timeout | Connect 2 s, response 30 s |
| Retry | None |
| Circuit breaker | **None.** An untested fallback is worse than an honest 502: it turns an outage into a silent wrong answer |
| Rate limit | **None yet** |

Public paths are an explicit configured list, not a pattern heuristic. `/api/auth/login` is
public; `/api/auth/me` is not. A prefix rule would expose most of the interesting surface.

### 4.4 Gateway endpoints

| Method | Path | Purpose | Phase |
|---|---|---|:--:|
| GET | `/actuator/health` | Liveness and readiness | 2 |
| GET | `/healthz` | NGINX-facing liveness | 0 |
| GET | `/internal/v1/gateway/info` | Services and routes | 3 |
| GET | `/.well-known/jwks.json` | RS256 public key set, for verifiers | 3 |

`/actuator/**` other than health is not exposed. `/actuator/env` and `/actuator/heapdump` on a
public entry point are reconnaissance for anyone who can reach the port.

## 5. Auth Service

Port 8081. Owns `nexa_auth`. The only service that ever handles a password.

### 5.1 Public endpoints

**As implemented in Phase 1.** All paths below are verified by
`AuthFlowIntegrationTest` and `PasswordFlowIntegrationTest`.

| Method | Path | Auth | Purpose |
|---|---|:--:|---|
| POST | `/api/v1/auth/register` | no | Create an account. Returns **no tokens**. |
| POST | `/api/v1/auth/login` | no | Exchange credentials for tokens, set as HTTP-only cookies |
| POST | `/api/v1/auth/refresh` | cookie | Rotate both tokens |
| POST | `/api/v1/auth/logout` | cookie + CSRF | Revoke this session. 204 regardless |
| POST | `/api/v1/auth/logout-all` | cookie + CSRF | Revoke every session |
| GET | `/api/v1/auth/me` | bearer | Current principal |
| POST | `/api/v1/auth/email/verify` | no | Verify an email (JSON body) |
| POST | `/api/v1/auth/email/verify-link` | no | Verify from a clicked link (`?token=`) |
| POST | `/api/v1/auth/password/forgot` | no | Request a reset. Always the same answer |
| POST | `/api/v1/auth/password/reset` | no | Complete a reset |
| POST | `/api/v1/auth/password/change` | bearer + CSRF | Change password. Requires the current one |

**Deviations from the original draft, and why.**

| Change | Reason |
|---|---|
| `/email/verify-link` added | A GET link would make verification a state change on navigation, which is what CSRF protection exists to prevent. The POST endpoint stays the primary. |
| `/logout` requires CSRF | It is a state-changing request on a cookie-authenticated session. Logout CSRF is low severity, but the protection costs nothing and the draft exempted it by oversight. |
| `logout-all` added | Revoking every session is a distinct, useful action. |
| Cookies are primary, `Authorization` accepted | Browsers cannot set headers, so cookies are how a browser sends an access token. The header fallback keeps curl, the gateway and service-to-service calls working. |

### 5.2 Token delivery

Both tokens are set as **HTTP-only cookies** and are **absent from every response body**.

| Cookie | Path | SameSite | HttpOnly | Secure |
|---|---|:--:|:--:|:--:|
| `nexa_access_token` | `/` | `Strict` | yes | yes |
| `nexa_refresh_token` | `/api/v1/auth/refresh` | `Strict` | yes | yes |

The refresh cookie is **scoped to the refresh endpoint** so it is not attached to every request.
`Secure` is false only under the `local` profile; anywhere else it must be true.

**The trade-off, stated plainly.** Cookies are sent automatically, so cookie-based auth requires
CSRF protection, which a bearer-header API does not. That is why CSRF is enabled, why
`SameSite=Strict` is the default, and why the pre-authentication endpoints are the only
exemptions.

### 5.3 Internal endpoints

Reachable only with the internal authority, which a user token never carries.

| Method | Path | Purpose |
|---|---|---|
| GET | `/internal/v1/auth/info` | Boundary assertion. Reports `nexa_auth` |
| POST | `/internal/v1/auth/introspect` | Verify a token. Returns `active: false`, never 401 |
| GET | `/internal/v1/auth/users/{id}/status` | Status, lock and verification flags |

### 5.3 Principal claims

```json
{
  "sub": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
  "iss": "nexa-auth-service",
  "aud": "nexaai-web",
  "roles": ["USER"],
  "status": "ACTIVE",
  "jti": "b7d9e1a4-3c2f-4a6b-8e5d-1f3a7b9c2e60",
  "iat": 1768473000,
  "exp": 1768473900
}
```

**Verification requirements, all mandatory.**
- `alg` must be exactly `RS256`. `alg: none` and an HS256 token signed with the public key are
  rejected.
- `iss` must be `nexa-auth-service`.
- `aud` must include `nexaai-web`.
- `exp` must be in the future.
- `status` must be `ACTIVE`. A suspended account's token is rejected even before it expires.

### 5.4 Registration

```http
POST /api/v1/auth/register
Content-Type: application/json
Idempotency-Key: 7f3a...

{ "email": "user@example.com", "password": "a-long-passphrase", "displayName": "Ada" }
```

**201 Created**
```json
{
  "userId": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
  "email": "user@example.com",
  "displayName": "Ada",
  "roles": ["USER"],
  "status": "PENDING_VERIFICATION",
  "createdAt": "2026-01-15T10:30:00Z"
}
```

**No token is returned from registration.** The account must verify its email first. This
prevents mass unverified registration and keeps the verification path real.

**409** if the email is already registered. The message must not reveal whether the existing
account is verified.

### 5.5 Login

```http
POST /api/v1/auth/login
{ "email": "user@example.com", "password": "a-long-passphrase" }
```

**200 OK**
```json
{
  "accessToken": "eyJhbGciOiJSUzI1NiIs...",
  "refreshToken": "9d1f...",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {
    "userId": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
    "email": "user@example.com",
    "displayName": "Ada",
    "roles": ["USER"]
  }
}
```

**Failure.** A wrong password and an unknown email return the **same** body and the **same**
status:

```json
{
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "Email or password is incorrect.",
    "correlationId": "...",
    "timestamp": "...",
    "details": null
  }
}
```

Timing must also be indistinguishable, which means a dummy hash is computed when the email does
not exist ([`SECURITY.md`](SECURITY.md) §2.1).

**429** after too many failures for one account.

### 5.6 Refresh

```http
POST /api/v1/auth/refresh
{ "refreshToken": "9d1f..." }
```

Returns a **new** access token and a **new** refresh token. The old refresh token is revoked. If
a revoked token is presented, the entire token family is revoked, because presentation of a
revoked token indicates theft.

**401** on an unknown, expired, already-used or revoked token.

### 5.7 Internal: introspect

```http
POST /internal/v1/auth/introspect
Authorization: Bearer <the token to verify>
```

**200**
```json
{ "active": true, "sub": "...", "roles": ["USER"], "status": "ACTIVE", "exp": 1768473900 }
```

**200 with `"active": false`** for an invalid token, rather than 401, so a caller can distinguish
"invalid" from "I called this wrongly". Never returns why.

### 5.8 Auth Service data

**As built in Phase 1.** Migration `V1__auth_schema.sql` in
`backend/auth-service/src/main/resources/db/migration/`. All tables in `nexa_auth`; no other
service's role can read any of them.

| Table | Purpose | Notes |
|---|---|---|
| `auth_user` | Email, password hash, status, role, `credentials_version`, `google_subject` | No plaintext password, ever. A `CHECK` makes "locally registered without a password" and "Google-only with a password hash" both impossible to persist |
| `refresh_token` | **Hashed** token, `family_id`, expiry, revoked_at, source | Rotation and theft detection |
| `token_denylist` | Revoked `jti` until natural expiry | Durable record; Redis mirrors it for speed |
| `auth_event` | Every authentication event, with IP and user agent | The lockout signal and the audit trail |
| `one_time_token` | **Hashed**, purpose-separated, single use, `attempt_count` | Email verification and password reset share the table, separated by `purpose` |
| `outbox_event` | Transactional outbox for `auth.*` events | Written with the account row, so the event cannot be lost or orphaned |

**Role and status are `VARCHAR` with a `CHECK` constraint, not lookup tables.** The enum in Java
is the source of truth, so a lookup table would add a join on every read to model something the
code already knows. The `CHECK` still makes a third role impossible at the database level, which
is the guarantee that matters. Verified by `DatabaseOwnershipIntegrationTest.onlyTwoRolesExist`.

**Security state commits independently of the rejection that triggers it.** The failed-login
counter and the refresh-token family revocation both happen immediately before an exception is
thrown. Inside the request's own transaction they would be rolled back with it — so lockout would
never engage and a detected stolen token would stay usable. `SecurityStateWriter` writes them in
`REQUIRES_NEW`. Both were caught by integration tests, not by inspection.

### 5.9 Google OAuth

**As built in Phase 1.** Initiated at `/oauth2/authorization/google`, callback at
`/login/oauth2/code/google`.

| Rule | Reason |
|---|---|
| Issues **NexaAI's own** tokens, never Google's | One token format for eight services; Google's availability is not on the critical path of every request |
| **No Google password is ever seen or stored** | The provider authenticates; this service receives only an assertion. A Google-only account has `password_hash IS NULL`, asserted by test |
| Account is created only if Google asserts `email_verified` | Otherwise anyone who can make Google accept an address could claim the account |
| The **`sub` claim is the identity key**, not the email | An email can change; `sub` cannot. Keying on email would let anyone who acquires an address take over the account |
| A changed email for a known `sub` resolves to the **stored** account | The person is the same; the asserted email cannot redirect the session |
| An email already linked to a **different** `sub` is refused | Otherwise controlling one Google account takes over an unrelated account sharing the address |
| Account **status is checked after resolution, for every path** | An earlier version returned on a `sub` match without checking status, so a suspended user could sign in via Google. Found by `suspendedAccountIsRefused` |
| Redirect target read from **configuration**, never the request | A login-callback redirect derived from a parameter is an open redirect, and a phishing vector |
| No token in the redirect URL | A token in a fragment lands in browser history and `Referer` headers |
| Registration is **programmatic and conditional** | A YAML block with an empty `client-id` makes Spring Boot fail startup with "Client id must not be empty", which would make Google load-bearing for everyone |

### 5.10 OpenAPI

Served at `/v3/api-docs`, with a UI at `/swagger-ui.html`. Public, because a contract nobody can
read is not a contract.

## 6. User Service

Port 8082. Owns `nexa_user`.

### 6.1 Endpoints

**Self-service. No route here takes a user identifier.** The caller comes from the verified
token, never from the request. This is the structural guarantee that one caller cannot read
another's data: there is no parameter to put someone else's id in.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/me` | Own profile |
| PATCH | `/api/v1/me` | Display name and avatar only |
| GET | `/api/v1/me/preferences` | Own preferences |
| PATCH | `/api/v1/me/preferences` | Partial update; absent fields unchanged |
| GET | `/api/v1/me/status` | Own status, reason, and own history |

`PATCH /api/v1/me` accepts **no** `email`, `role`, `accountStatus` or `authUserId` field. Those
are owned elsewhere, and an endpoint that accepts them is a privilege escalation. Their absence
from the request type is the control.

**Administrative.** Requires `ADMIN`. Users are addressed by **auth-service id**, the
platform-wide identity; the internal surrogate id means nothing outside this service.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/admin/users` | List: filter by `status`/`role`, `search`, page |
| GET | `/api/v1/admin/users/counts` | Counts by status |
| GET | `/api/v1/admin/users/{id}` | Detail, including the full status history |
| GET | `/api/v1/admin/users/{id}/usage` | Subscription and usage |
| POST | `/api/v1/admin/users/{id}/activate` | |
| POST | `/api/v1/admin/users/{id}/suspend` | **Reason required** |
| POST | `/api/v1/admin/users/{id}/deactivate` | Permanent; no transition leaves it |
| POST | `/api/v1/admin/users/{id}/status` | The general form of the three above |

Three deliberate choices worth stating:

- **A suspension requires a reason**, which is shown to the account holder. An unexplained block
  is a support ticket, not an administrative decision.
- **The account holder's own history omits the acting administrator.** They need to know a
  suspension happened and why; they do not need the operator's identity. The admin view does
  include it.
- **Unknown query filters are rejected, not ignored.** Silently dropping a misspelled `status`
  and returning every user is how a response gets cached and screenshotted.

### 6.2 Profile shape

```json
{
  "id": "3d0f7a55-6c21-4a3e-9f18-2b7c5e0d9a44",
  "authUserId": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
  "email": "user@example.com",
  "displayName": "Ada",
  "avatarUrl": null,
  "accountStatus": "ACTIVE",
  "role": "USER",
  "statusReason": null,
  "statusChangedAt": null,
  "planId": null,
  "planName": null,
  "emailVerified": true,
  "registeredVia": "PASSWORD",
  "createdAt": "2026-01-15T10:30:00Z",
  "updatedAt": "2026-01-15T10:30:00Z"
}
```

**No password, hash, or token field exists in this shape**, because none of them ever reaches
this service ([`SECURITY.md`](SECURITY.md) §11.1). There is no column to hold one either.

`accountStatus` here is a **projection** of Auth Service's authoritative status, kept so the
admin view can filter and explain without a network call per row and so a blocked user can see why
on their own profile. It is denormalised read state, not a second source of truth.

### 6.3 Consumes

| Topic | Action | Implemented |
|---|---|:--:|
| `auth.user.registered.v1` | Create the profile | **Yes** |
| `auth.user.email_verified.v1` | Mark verified | No |
| `subscription.activated.v1` | Attach the plan summary | No |
| `subscription.cancelled.v1` | Detach the plan summary | No |
| `user.status.changed.v1` | Republish an administrative change | No |

Consumption is **idempotent on `eventId`**, recorded in `processed_event` in the same transaction
as the profile insert. Kafka is at-least-once, so a replay must not produce a second profile;
the unique constraint on `auth_user_id` is the backstop when two consumers race.

The listener bean exists only when `NEXA_USER_EVENT_ENABLED` is true, so the service starts and
serves traffic with no broker present.

### 6.4 Produces

**Nothing yet.** Phase 2 implements no publisher. The three topics below are the intended
contract for later phases:

| Topic | Action |
|---|---|
| `user.profile.updated.v1` | Invalidate caches, update search indexes |
| `user.account.deleted.v1` | Trigger deletion across services |
| `user.status.changed.v1` | Notify chat and subscription services |

This is stated plainly because a contract listing topics that are never published is worse than
one that admits it has none.

### 6.5 Subscription and usage

`GET /api/v1/admin/users/{id}/usage` crosses a service boundary to Subscription Service over
HTTP, behind an interface. It does **not** read that service's database; doing so would violate
the same rule as reading Auth Service's.

Until Phase 9 exists the call is disabled and the response reports `available: false` with a
reason. It does **not** report zero: a zero reads as "this user has used nothing", which is a
different and wrong claim.

## 7. Chat Service

Port 8083. Owns `nexa_chat`. Orchestrates a chat turn.

### 7.1 Endpoints

| Method | Path | Auth | Purpose |
|---|---|:--:|---|
**Conversations are the sessions.** There is no separate session table: a session *is* a
conversation, and a second table would let the two disagree about what exists.

**No route accepts a user identifier.** Conversations and messages are addressed by their own id
and scoped to the caller by the query. Another user's conversation returns **404, not 403** �
a 403 confirms it exists, which is a reliable oracle for discovering real ids.

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/conversations` | Create. Body may be empty |
| GET | `/api/v1/conversations` | **Active** conversations. Excludes archived |
| GET | `/api/v1/conversations/archived` | Archived conversations |
| GET | `/api/v1/conversations/search?q=` | By title **or** message text |

#### Message shape

```json
{
  "id": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
  "conversationId": "3d0f7a55-6c21-4a3e-9f18-2b7c5e0d9a44",
  "sequenceNo": 2,
  "role": "ASSISTANT",
  "content": "",
  "status": "PENDING",
  "model": "nexa-default",
  "inputTokens": null,
  "outputTokens": null,
  "edited": false,
  "regenerated": false,
  "failureReason": null,
  "createdAt": "2026-01-15T10:30:00Z",
  "feedback": null
}
```

`status` is `COMPLETE`, `PENDING` or `FAILED`. **`PENDING` is the AI response placeholder, and
it is written before generation is attempted.** If the row were created afterwards, an
interrupted stream, a crashed process or a timeout would leave the user with a question, no
reply, and no evidence anything happened.

**Sending currently produces a `PENDING` placeholder and it stays `PENDING`.** Generation is not
wired in Phase 3. That is not an error: nothing failed, nothing was attempted. It is also not
fabricated content, and it is not `FAILED` � a failed badge on every reply would be a lie.

#### History is append-only

Editing a user message writes a **new** row and supersedes the old one; regenerating does the
same in reverse. Nothing is overwritten in place. Superseded rows remain in the table and are
excluded from the default history read.

The intuitive implementation mutates the row, which destroys the only record of what was
originally said � and since showing alternatives is the entire point of edit and regenerate, an
implementation that deletes the previous attempt cannot implement them correctly.

### 7.2 Streaming contract (Phase 5 � not implemented)

> **Not implemented.** Chat Service currently answers `POST /messages` with JSON, not
> `text/event-stream`. The shape below is the contract the SSE relay will implement in Phase 5,

```

Accept: text/event-stream

{ "content": "What does the cancellation policy say?", "ragEnabled": true }
```

**Response: `text/event-stream`**

```
event: meta
data: {"messageId":"...","conversationId":"...","model":"gpt-4o-mini","provider":"OPENAI"}

event: retrieval
data: {"used":true,"passageCount":3,"sources":[{"documentId":"...","title":"terms.pdf","chunkIndex":4}]}

event: token
data: {"text":"The cancellation window is "}

event: token
data: {"text":"30 days."}

event: citation
data: {"index":1,"documentId":"...","title":"terms.pdf","chunkIndex":4}

event: usage
data: {"promptTokens":812,"completionTokens":47,"totalTokens":859}

event: done
data: {"messageId":"...","status":"COMPLETE","finishedAt":"2026-01-15T10:30:04Z"}

event: error
data: {"code":"AI_PROVIDER_TIMEOUT","message":"The model did not respond in time.","retryable":true}
```

**Event semantics.**

| Event | Frequency | Meaning |
|---|---|---|
| `meta` | exactly once, first | Identifiers and the model selected |
| `retrieval` | 0 or 1 | What was retrieved, if RAG was on |
| `token` | many | One text fragment. Concatenate in order |
| `citation` | 0+ | A source used. Must accompany any grounded answer |
| `usage` | exactly once | Token counts for metering |
| `done` | exactly once, last | Terminal success |
| `error` | at most once, last | Terminal failure. No `done` after it |

**Rules.**
- Exactly one terminal event, `done` or `error`.
- An `error` after some `token` events means the answer is **partial**. The stored assistant
  message is marked incomplete, never complete.
- The client must tolerate a dropped connection: it reconnects and reads the persisted message.
- Every proxy hop must disable buffering, or the stream arrives all at once
  ([`ARCHITECTURE.md`](ARCHITECTURE.md) §13, decision 021).

### 8.2 Generate request

```json
{
  "model": "nexa-default",
  "message": "Explain the CAP theorem in two paragraphs.",
  "conversationId": "0f9c1e2a-4b7d-4f1e-9a3c-2d5e6f708192",
  "temperature": 0.7,
  "maxOutputTokens": 1024
}
```

| Field | Required | Notes |
|---|:--:|---|
| `message` | yes | 1–320,000 characters. Blank is a 400 |
| `model` | no | Absent means the configured default, named explicitly so behaviour does not change when the catalogue is reordered |
| `conversationId` | no | Correlation only. Never forwarded to a provider |
| `temperature` | no | 0–2. **Refused with 400 for a model that does not support it** |
| `maxOutputTokens` | no | Clamped to the model's limit and a platform ceiling the caller cannot raise |

Two deliberate omissions:

- **No `systemPrompt`.** A caller who could set the system instruction would be instructing the
  model directly, which is prompt injection with an HTTP parameter. System instructions come from
  AI Service, if at all.
- **No `messages` array.** One user turn. Conversation history belongs to Chat Service, which owns
  it; a second copy here would be a second thing to keep in sync and a second place to leak message
  content.

`maxOutputTokens` is not required, but it is **always** bounded: an absent value resolves to the
configured default, which is itself clamped. A missing bound must not mean an unbounded bill.

### 8.3 Generate response

```json
{
  "requestId": "0f9c1e2a-4b7d-4f1e-9a3c-2d5e6f708192",
  "content": "...",
  "model": "nexa-default",
  "provider": "OPENAI",
  "inputTokens": 812,
  "outputTokens": 47,
  "fallbackUsed": false,
  "streamed": false,
  "durationMillis": 1423,
  "completedAt": "2026-10-06T19:41:22.104Z"
}
```

`model` is the model that **actually answered**, which may not be the one requested. `fallbackUsed`
says so explicitly rather than leaving the caller to infer it by comparing.

`inputTokens` / `outputTokens` are `null` when the provider reported no usage. **Never zero.** Zero
would assert that the provider reported none; null says it reported nothing, which is a different
and honest statement.

### 8.4 Stream contract

`POST /internal/v1/ai/generate/stream` → `text/event-stream`. Frame shape: an `event:` line and a
`data:` line together, terminated by a blank line.

| Order | Event | `data` |
|:--:|---|---|
| 1 | `meta` | `{"requestId":"…","model":"…","provider":"…"}` |
| 2..n | `token` | `{"text":"…"}` — one per chunk, emitted as produced |
| last | `done` | `{"requestId":"…","status":"COMPLETE","durationMillis":…}` |
| — | `error` | `{"code":"…","message":"…","retryable":true\|false}` — replaces everything after `meta` |

Rules, all of which a client depends on:

- **Chunks are separate events.** A single event carrying the whole answer renders identically to no
  stream at all.
- **The stream always terminates** with `done` or `error`. A stream that simply closes leaves the
  client unable to distinguish a finished generation from a dropped connection, so it waits forever.
  A truncated stream is reported as `error` with code `STREAM_TRUNCATED`, never as success.
- **`error.retryable` is authoritative.** It is false for a request the provider refused and true for
  a transient fault. The frontend offers Retry only when it is true.
- **`meta` arrives first**, so a client can show which model is answering before any content does.
- Availability is checked **before the stream opens**. A stream that opens and then fails leaves the
  client holding a connection to nothing, and makes "no provider configured" look like a network
  error.

Token text is JSON-escaped by AI Service, including control characters. They are escaped rather than
dropped, because dropping them would silently corrupt the answer the user is reading.

### 8.5 Model availability

`GET /internal/v1/ai/models` returns **every configured model, available or not**:

```json
[
  { "name": "nexa-default", "provider": "OPENAI", "priority": 1,
    "supportsTemperature": true, "maxInputTokens": 128000, "maxOutputTokens": 4096,
    "available": true, "unavailableReason": null, "allowFallback": true },
  { "name": "nexa-gemini-flash", "provider": "GEMINI", "priority": 1,
    "supportsTemperature": true, "maxInputTokens": 1000000, "maxOutputTokens": 8192,
    "available": false,
    "unavailableReason": "Provider Google Gemini has no credential configured.",
    "allowFallback": true }
]
```

Listing only what works would hide a misconfigured deployment from the person trying to fix it.
`unavailableReason` is the actionable part: "unavailable" alone tells an operator nothing, and this
tells them exactly which line to change. **A reason never contains a credential.**

### 8.6 Routing, fallback and retry

- **Selection.** A named model, else the configured default. An unknown name is a **400** that lists
  the real names — never a silent substitution of the default, which would answer a question about
  model A with model B and give the caller no way to know.
- **Fallback** is *within* the same provider by default, ordered by `priority`. A request for Gemini
  answered by Llama is a different product, not a graceful degradation, so crossing providers
  requires a per-model `allowCrossProviderFallback` opt-in.
- **The honest limit of same-provider fallback:** it cannot survive a provider *outage*, because when
  a provider is down every model behind it is down too. It covers the case where one model is
  rate-limited, overloaded or decommissioned while its siblings work.
- **Retry** repeats the *same* request, only for retryable failures, at most `maxAttempts` (default 3)
  with exponential backoff from 250 ms capped at 2 s. A retry policy that keeps a request alive for
  thirty seconds turns a provider outage into a slow failure for every caller at once.
- **Failure classification decides both.** Retry asks "would the same request work again?"; fallback
  asks "would a different model do better?" A rejected request answers no to both — retrying it is how
  one bad prompt becomes three provider calls and a slower failure.
- **Health.** A provider is marked unhealthy after 3 consecutive *retryable* failures and recovers
  after 30 s. Only retryable failures count: a provider answering "400 bad request" is a provider
  that is up, and treating that as an outage takes a working provider out of rotation.

### 8.7 Error mapping

| Failure kind | HTTP | `code` | Retryable upstream |
|---|:--:|---|:--:|
| `REJECTED` | 400 | `PROVIDER_REJECTED` | no |
| `LIMIT_EXCEEDED` | 400 | `PROVIDER_LIMIT_EXCEEDED` | no |
| `UNAUTHORISED` | 502 | `PROVIDER_UNAUTHORISED` | no |
| `UNKNOWN` | 502 | `PROVIDER_UNKNOWN` | no |
| `THROTTLED` | 503 | `PROVIDER_THROTTLED` | yes |
| `UNAVAILABLE` | 503 | `PROVIDER_UNAVAILABLE` | yes |
| `NOT_CONFIGURED` | 503 | `PROVIDER_NOT_CONFIGURED` | yes, later |

Plus `UNKNOWN_MODEL` (400, lists the real names) and `NO_PROVIDER_AVAILABLE` (503, carries the
per-candidate reasons).

The split that matters: a refusal the provider attributes to the **request** is a 400, and one it
attributes to **our credential or wiring** is a 502. Collapsing them would tell a caller to fix a
prompt that is fine. **No provider's own message is ever returned** — it may name an upstream URL or
an account. Fixed text per kind is returned; the provider's message goes to the log.

### 8.8 Produces

None. AI Service publishes no Kafka topic in this phase.

Usage is recorded **in memory only** and exposed at `/internal/v1/ai/usage`, precisely because the
service owns no database. `UsageSink` is an interface so a later phase replaces the bean with one
that persists and nothing above it changes.

A usage record carries counts and identifiers and **never prompt or completion text**. A usage
record is the thing most likely to be logged, exported to a metrics backend and kept for a year;
carrying a user's words through all of that would turn metering into a data-retention problem nobody
asked for. It also carries no user identifier — this service holds no user data at all.

### 8.9 Chat Service relay

`POST /api/v1/conversations/{conversationId}/messages` stores a message and creates the assistant
placeholder. Streaming is a **separate** route, not a flag on that one:

`POST /api/v1/conversations/{conversationId}/messages/stream` → `text/event-stream`

| Property | Value |
|---|---|
| Ownership | Checked **before** the stream opens. Another user's conversation returns the same 404 as one that does not exist |
| Event shape | Identical to §8.4. Frames are re-assembled and re-emitted, never re-interpreted — two implementations of one contract can disagree, and a disagreement shows up as a browser rendering the wrong chunk at the wrong time |
| Upstream error status | Converted to a single `error` event, never a bare HTTP status — the browser has already committed to a stream, so a status it can no longer read is a failure the user sees as a silently stopped stream |
| Relay read timeout | **None.** A generation may legitimately take minutes; cutting it off leaves a partial answer with no error |
| Connect timeout | 5 s. An unreachable AI Service should fail fast rather than hold the connection for the full emitter timeout |
| Emitter timeout | 5 minutes, bounded and configurable. It bounds holding a connection open with nothing to say, not generation |
| Threading | Virtual thread. `SseEmitter.send` blocks until the browser consumes each frame, so doing this inline would pin a container thread for the whole generation |

**Retry semantics:** retrying a generation re-opens the stream **only**. The question is already
stored, and re-sending it would put two identical questions in the thread with one answer between
them.

### 12.1 Ownership

### 12.2 Envelope

Every event uses one envelope:

```json
{
  "eventId": "b7d9e1a4-3c2f-4a6b-8e5d-1f3a7b9c2e60",
  "eventType": "chat.message.completed.v1",
  "eventVersion": 1,
  "occurredAt": "2026-01-15T10:30:04Z",
  "correlationId": "0f9c1e2a-4b7d-4f1e-9a3c-2d5e6f708192",
  "actorId": "9f1c7b2e-4a3d-4c8f-b1e2-5d7a9c3e0f14",
  "subjectId": "3c5a...",
  "payload": { }
}
```

**Rules.**
- `eventId` is the idempotency key. A consumer deduplicates on it.
- `correlationId` ties the event to the request that caused it. Without it, a bug report cannot
  be traced.
- `actorId` is who caused it; `subjectId` is what it happened to. An admin acting on a user has
  different values.
- **No secret, no prompt content and no document content in any payload.** Analytics needs
  counts, and counts are what it gets.

### 12.3 Naming

`<domain>.<entity>.<past-tense-verb>.v<N>`, lowercase, dot-separated.

Facts, never commands: `chat.message.completed.v1`, not `send-chat-message.v1`. A consumer
should not need to know what to do, only what happened.

### 12.4 Evolution

| Change | Compatible |
|---|---|
| Add a field | yes |
| Add an enum value | yes |
| Remove a field | no — deprecate, retain, remove at a version bump |
| Rename or retype a field | no |
| Change a field's meaning | no — that is a new event type |

A consumer must ignore unknown fields. A producer must never change the meaning of an existing
field.

### 12.5 Delivery

At-least-once. Therefore:

- Every consumer is idempotent, deduplicating on `eventId`.
- Events are not delivered in order across partitions; ordering holds only within a partition,
  and only for the same key.
- A consumer must tolerate an event arriving late, or twice, or after a restart.

## 13. Contract change discipline

| Change | Action |
|---|---|
| A new endpoint | Add to this document in the same change |
| An endpoint removed or its path changed | New version, deprecate the old, document both |
| A field added | Add here; consumers ignore unknown fields |
| A field removed | Deprecate, retain, remove at a version bump |
| A new event | Add to §12 with its owner, consumers, partitions, key and retention |
| A topic's owner changes | A new topic. One producer owns a topic for its lifetime |
| Any change | Update this document **in the same commit** ([`RULES.md`](RULES.md) §12) |

**A contract change without a documentation change is an incomplete change.** The document is
the shared artefact that replaces a shared code module
([`ARCHITECTURE.md`](ARCHITECTURE.md) §13, decision 013).
