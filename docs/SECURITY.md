# SECURITY.md — Security Model

Threats, controls and known gaps for NexaAI.

**Current state: Phase 0.** Nothing here is implemented. This document is the specification that
Phases 1–12 are measured against, and the checklist used in Phase 11. A control listed as
"planned" is **not** a control that exists.

---

## 1. Threat model

### 1.1 What we are defending

| Asset | Why it matters |
|---|---|
| User credentials | Direct account takeover |
| Documents | Private, potentially confidential, owned by one user |
| Conversations | May contain anything the user typed |
| Access and refresh tokens | Bearer tokens; possession is access |
| Payment details | Razorpay test mode only, but still must be handled correctly |
| AI provider keys | Cost and provider-account abuse |
| Service database credentials | Would allow a cross-service breach |
| Audit records | Must be trustworthy, or the rest of the log is unreliable |

### 1.2 Adversaries

| # | Adversary | Capability |
|---|---|---|
| A1 | Anonymous internet user | Can reach the edge and the login endpoints |
| A2 | Authenticated user (A) | Legitimate session, deliberately targets user B |
| A3 | Malicious user | A2 plus crafted uploads and crafted prompts |
| A4 | Compromised dependency | Executes inside the build or the runtime |
| A5 | Insider with log or backup read access | Read access to widely distributed data |
| A6 | Network attacker | Eavesdrops or intercepts, if TLS is missing |

### 1.3 Assumptions

- The host is not owned by the attacker.
- TLS is terminated at the edge in any non-local environment.
- Secrets are held in a secret store, not in images or source.

## 2. Authentication

### 2.1 Passwords

| Control | Detail | Phase |
|---|---|:--:|
| Hashing | Argon2id, or bcrypt at a current cost factor | 1 |
| Salt | Per-user, generated by the algorithm's own salt parameter | 1 |
| Never reversible | No encryption, no reversible encoding, ever | 1 |
| Never stored plaintext | Not in a column, not in a log, not in a queue, not in an exception | 1 |
| Never in transit | The password is never echoed back in any response | 1 |
| Reset | Single-use, time-limited token; the old password is invalidated | 1 |
| Policy | A minimum length is enforced; composition rules are not, because they push users toward predictable substitutions | 1 |
| Breach check | Optional, against a k-anonymity service, with clear user consent | 1 |

### 2.2 Tokens

| Property | Value | Rationale |
|---|---|---|
| Algorithm | **RS256** | Asymmetric, so verifiers need only the public key. An HS256 token signed with a leaked public key is a real attack class. |
| Access token TTL | 15 minutes | Short enough that a revocation propagates quickly |
| Refresh token TTL | 7–30 days, rotating | Long enough to be usable, rotating so theft is detectable |
| Refresh token storage | Hashed at rest | A database dump must not yield usable refresh tokens |
| Rotation | A new refresh token on every use; the old one is revoked | Reuse is detectable |
| Claims | `sub`, `iss`, `aud`, `roles`, `jti`, `iat`, `exp` | `jti` enables revocation; `iss`/`aud` stop cross-service replay |
| Signing key | RS256 private key from the filesystem or a secret store, outside the repository | Never in source or in an image |
| Revocation | Denylist in Redis with a TTL ≥ the token lifetime | Bounded and self-healing |

**Algorithm confusion must be rejected.** The verifier must check `alg` against an allowlist of
exactly one expected algorithm, and must never trust the header. `alg: none`, and an HS256
token signed with the public key, are both rejected. This is tested
([`TEST_PLAN.md`](TEST_PLAN.md) §7).

### 2.3 Session handling

- Access tokens in memory in the browser. Refresh on application load, not on a timer.
- No token in a URL. URLs end up in browser history, proxy logs and `Referer` headers.
- Sign-out revokes the refresh token and clears client state.
- `Authorization` header only. No token in a cookie, so CSRF does not apply to the API.
- Absolute timeout on a session regardless of activity.

## 3. Browser storage

| Value | Where | Why |
|---|---|---|
| Access token | **Memory** (a closure or a context), never storage | Unreadable by any injected script |
| Refresh token | Memory, or an `HttpOnly; Secure; SameSite=Strict` cookie if chosen | Not readable from JavaScript |
| Theme, sidebar width | `localStorage` | A UI preference, not a secret |

**AI provider API keys are never in the browser.** Vite inlines every `VITE_*` variable, so
anything prefixed `VITE_` is public ([`RULES.md`](RULES.md) §6). Only the AI Service holds those
keys.

This is enforced by three independent properties, not by convention:

1. **No gateway route exists for AI Service.** The service is reachable only from Chat Service on
   the internal network. Publishing it would put every provider credential one hop from the
   internet, with nothing but a future route change standing between them and a browser.
2. **The only credential the browser can send is a cookie.** The streaming client in
   `frontend/nexa-ai-web/src/api/stream.ts` reads the CSRF cookie and nothing else. There is no
   `Authorization` header, no `VITE_*` credential, and no code path that could construct one.
3. **No response ever contains a key.** Availability reasons, health snapshots and usage records
   are asserted by `NoCredentialExposure` in `AiAuthorizationTest` to contain no credential
   pattern — an availability reason is exactly the sort of text someone pastes a key into by
   accident, because it is the one place an operator looks first when a provider is "not working".

**Token relay, and why it is scoped.** Chat Service forwards the caller's own access token to AI
Service so the request that reaches a model is attributable to the user who made it rather than to
Chat Service asking anonymously. The token is held in `CallTokenHolder`, a request-scoped bean, and
**not** on `AuthenticatedCaller` — whose `getCredentials()` deliberately returns null, because the
authentication object travels through the security context, the audit trail and log statements, and
the principal must not be able to read its own credential. The holder is cleared in a `finally`, so
a mid-request exception cannot leave a credential attached to a pooled thread that Tomcat then
hands to the next request.

**Service-to-service authentication is relay, not a second identity.** AI Service verifies the
same token it would verify from a browser, with the same RS256 public key. That is weaker than a
service credential carrying its own identity, and deliberately so for now: a second token type
means a second issuer path, a second audience and a second thing to get wrong. The gap is recorded
rather than papered over — see [`ARCHITECTURE.md`](ARCHITECTURE.md) §16c.

**What a provider credential can reach, and who can reach it.** An AI Service key is billable
capacity. The blast radius of leaking one is therefore bounded by three things: it is never in the
bundle, never in a response, and never loggable — `SpringAiProviderClient` logs a provider id and
the *fact* that a credential is present, never the value.

`localStorage` is readable by any script on the origin. A cross-site scripting bug therefore
becomes a credential theft bug, which is why §8 treats XSS as a security requirement and not
just a rendering bug.

## 4. Authorization

### 4.1 Two roles

Exactly `USER` and `ADMIN` ([`RULES.md`](RULES.md) §8). No `SUPER_ADMIN`, no `MODERATOR`, no
`SUPPORT`.

### 4.2 Principles

1. **Enforce server-side, on every request.** The frontend hiding a button is a usability
   feature, not a security control.
2. **Roles come from the token, and the token is verified.** A role in a request body, a query
   parameter or a header set by the client is ignored.
3. **Ownership is checked, not assumed.** A `USER` may act only on their own resources, so a
   known id is not authorisation.
4. **Return 404, not 403**, for a resource that exists but belongs to someone else. Returning
   403 confirms it exists. `ADMIN` is the exception and may see 403.
5. **Deny by default.** A route with no explicit rule is closed.
6. **The gateway is the first check, not the only one.** Each service re-verifies, because a
   service reachable from inside the network must not trust the edge blindly.

### 4.3 The matrix

Every row is a test ([`TEST_PLAN.md`](TEST_PLAN.md) §5): a USER cannot read or modify another
user's profile, conversations, documents or vectors; anonymous callers reach no authenticated
route; a USER token is rejected on every admin route.

## 5. Secrets

### 5.1 Rules

| Rule | Detail |
|---|---|
| Source of truth | Environment variables or a secret store |
| Never in source | No key, password or secret in any tracked file |
| Never in images | Not as a build arg, not as a copied file, not in a layer |
| Never in the frontend | No AI key, no payment secret, no signing key ([`RULES.md`](RULES.md) §6) |
| Never in logs | Including exception paths, where a configuration value is easy to print by accident |
| Never in error responses | A stack trace to a client is an information leak |
| Only `.env.example` is tracked | With empty placeholders |
| `.env` is gitignored | And verified untracked by CI |

### 5.2 What is a secret here

| Secret | Held by |
|---|---|
| `OPENAI_API_KEY` | ai-service, rag-service (embeddings) |
| `GEMINI_API_KEY` | ai-service, rag-service |
| `GROQ_API_KEY` | ai-service |
| JWT RS256 private key | auth-service |
| Per-service database passwords | that service only |
| `RAZORPAY_TEST_KEY_SECRET` | subscription-service only |
| `RAZORPAY_WEBHOOK_SECRET` | subscription-service only |

### 5.3 What is deliberately not a secret

| Value | Why |
|---|---|
| `RAZORPAY_TEST_KEY_ID` | A public identifier; Razorpay intends it in the browser |
| `VITE_API_BASE_URL` | Public by definition |
| Database *names* | Structure, not credential |

### 5.4 Rotation

Every secret has a documented rotation procedure, and Phase 11 rehearses it with real
downtime. A rotation procedure that has never been executed is a hypothesis.

### 5.5 CI enforcement

Credential-shaped strings are scanned on every push: `sk-…`, `AIza…`, `rzp_live_…`, `ghp_…`.
Tracked `.env` files fail the build. Any `.env.example` containing a value that is not empty,
`localhost`, `http://` or `127.0.0.1` fails the build.

**Git history note.** Removing a secret from the working tree does not remove it from history.
If a real credential is ever committed, rotation is mandatory and immediate. History rewriting
alone is not a remedy.

## 6. Rate limiting and abuse control

### 6.1 Limits

| Scope | Limit | Rationale |
|---|---|---|
| Auth, per IP | 10 req/min | Credential stuffing |
| Auth, per account | 5 failures/min, then lock | Brute force |
| Chat, per user | concurrent stream limit | Cost. A stream is a live provider connection |
| Chat, per IP | 60 req/min | General abuse |
| API, per IP | 300 req/min | General abuse |
| Upload, per user | size and count | Storage and extraction cost |
| Search, per user | per-minute | Embedding cost |

### 6.2 Where it is enforced

**Two layers, deliberately.** The edge (NGINX) limits by IP and rejects absurd bodies before
they tie up a connection. Each service limits by user, because a single NAT'd IP can be many
legitimate users and a single user can have many IPs. The edge cannot know the user; the service
cannot see the raw IP cheaply. Neither layer replaces the other.

### 6.3 Fail behaviour

Rate limiting returns 429 with `Retry-After`. It must never be implemented as a silent drop or a
queued retry: a user who is being limited needs to know.

### 6.4 Cost-based abuse

Because each message costs money, an untrusted client must never be able to choose an unbounded
model or an unbounded parameter. The model catalogue and its limits are server-side. A client
requesting a model it is not entitled to is rejected before the provider is called.

## 7. File security

Documents are the most dangerous user-supplied input in this system: they are stored, parsed and
later fed to a model.

| Control | Detail | Phase |
|---|---|:--:|
| Allowlist formats | PDF, plain text, Markdown, DOCX. Never a binary executable | 6 |
| **Validate content, not extension** | The file's magic bytes are checked. A renamed executable is rejected | 6 |
| Size limits | Per file and per user, enforced before full buffering, and at the edge | 6 |
| Storage outside the web root | Never under a directory a server can execute or serve directly | 6 |
| Random filenames | Generated server-side. The client filename is metadata, never a path | 6 |
| No path traversal | The client filename is never used to build a path | 6 |
| Never executed | Never run, never interpreted, never served with its original content type | 6 |
| Owner-only access | Always served through an authorised controller | 6 |
| Delete on request | The user can delete a document and its derived vectors | 6, 7 |
| Parser isolation | Extraction runs with no network and no shell access | 6 |
| Virus scanning | Planned for Phase 11 | 11 |

**Why content validation matters more than the extension.** The extension is chosen by whoever
uploads the file. The magic bytes are a property of the file. Checking the extension and
believing it is the vulnerability.

## 8. Injection

| Injection | Control | Phase |
|---|---|---|
| SQL injection | Parameterised queries via JPA or the JDBC driver. No string concatenation. Identifiers validated against an allowlist | 1+ |
| NoSQL injection | Not applicable: PostgreSQL is the only datastore | — |
| XSS | React escapes by default; **no `dangerouslySetInnerHTML` on unsanitised content**; model markdown sanitised before rendering | 10 |
| Command injection | No shell invocation anywhere. If a tool must be run, arguments are passed as an array, never a string | 6 |
| SSRF | The system makes no user-directed outbound request. A document may not contain a URL the server fetches | 6 |
| **Prompt injection** | Retrieved passages are wrapped and labelled as untrusted data; the system prompt forbids document content from changing instructions | 8 |

**Prompt injection is called out separately** because it has no complete fix. The mitigations
reduce its effect; they do not eliminate it. What must never happen is a document causing an
action with side effects outside the AI's answer. The system holds no tool-calling capability,
which is a deliberate product decision that reduces this risk substantially
([`PRD.md`](PRD.md) §1.3).

The `text()` response header is set wherever untrusted text can appear, and the gateway sets
`Content-Security-Policy`.

## 9. Payment security

Test mode only ([`RULES.md`](RULES.md) §9).

| Control | Detail | Phase |
|---|---|:--:|
| Test mode enforced | The service refuses to start unless the mode is `test`. **No live-mode variable exists** | 9 |
| Amount server-side | Read from the plan in the database, never from the client | 9 |
| Currency server-side | Same | 9 |
| Signature verification | Constant-time comparison of the webhook HMAC, before any payload is trusted | 9 |
| Webhook is the source of truth | Not the browser redirect. Closing the tab must not lose a payment | 9 |
| Idempotency | Keyed on the provider payment id, because providers retry | 9 |
| No card data | The browser talks to Razorpay. **NexaAI never sees or stores a card number** | 9 |
| Public key only | The test key id may reach the browser; the secret may not | 9 |
| Audit | Every payment event recorded | 9, 11 |

## 10. Transport and edge

| Control | Detail | Phase |
|---|---|---|
| TLS | Everywhere in any non-local environment | 11 |
| HSTS | `Strict-Transport-Security` with a long max-age | 11 |
| HSTS preload | Optional | 11 |
| `X-Content-Type-Options` | `nosniff` | 0 (config) |
| `X-Frame-Options` | `DENY`, or a CSP `frame-ancestors` | 0 (config) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 0 (config) |
| `Permissions-Policy` | Deny camera, microphone, geolocation | 0 (config) |
| `server_tokens` | `off` | 0 (config) |
| CSP | Deferred from Phase 0, settled and applied in Phase 10 | 10 |
| CORS | An explicit origin allowlist at the gateway. **Never `*` with credentials** | 3 |
| Internal endpoints | `/internal/**` and `/actuator/**` unreachable externally — denied at the edge *and* by the gateway | 3 |
| Body size | Capped at the edge as well as in the service | 0, 6 |
| Timeouts | On every internal call, so one slow service cannot exhaust a thread pool | 3 |

**A note on CSP.** No Content-Security-Policy is set in Phase 0. A wrong CSP breaks the
application in a way that looks like a bug, and the real policy depends on how Phase 10 builds
the frontend. Setting it in Phase 0 would be guessing. It is tracked, not forgotten.

## 11. Logging and audit

### 11.1 What may be logged

- Correlation id, service, timestamp, level, route, method, status, latency
- User id, for actions on a user's own data
- Provider and model name, token counts, latency — **not the prompt or the completion**
- Document id and state transitions — **not the document content**

### 11.2 What may never be logged

| Never | Why |
|---|---|
| Passwords, in any form | Credential exposure |
| Tokens, whole or truncated | A truncated JWT is still a bearer credential |
| API keys, payment secrets | Credential exposure |
| Prompt or completion content | It is the user's data, and logs are widely readable |
| Document content | Same |
| Raw request or response bodies | They contain the above |

### 11.3 Audit requirements

Audit is distinct from logging. It answers *who did what, to whom*, and is treated as
append-only.

| Event | Recorded |
|---|---|
| Login success and failure | actor, IP, timestamp, user agent, outcome |
| Logout, token refresh, revocation | actor, timestamp |
| Account registration and email verification | actor, timestamp |
| Password change and reset request and completion | actor, timestamp, source IP |
| Every admin action | actor, action, target, before and after, timestamp |
| Account suspension and reinstatement | actor, target, reason, timestamp |
| Plan and model catalogue changes | actor, before and after, timestamp |
| Payment events | user, provider payment id, order id, amount, status |
| Document deleted | actor, document id, size, timestamp |
| Data export or deletion request | actor, scope, timestamp |

**Properties.**
- **Append-only.** Audit records are never updated or deleted, including by an admin.
- **Separate from application logs**, so clearing logs does not erase the audit trail.
- **Timestamped**, by a trusted source.
- **Retention is documented** and stated to users.
- **Monitored for gaps.** A missing audit record is itself an alert.

## 13a. Phase 1 status — what auth-service actually implements

Added after Phase 1. These are no longer gaps; each is asserted by a named test.

### 13a.1 Implemented and tested

| Control | Evidence |
|---|---|
| Passwords hashed with Argon2id, never reversible or logged | `AuthFlowIntegrationTest`, single `PasswordEncoder` bean |
| Password never present in any DTO | `noCredentialInAnyDto` reflects over the response records |
| No user enumeration, in response **or** timing | `noUserEnumeration`; `burnTimeOnMissingUser` runs a real Argon2 verification |
| RS256 with the algorithm pinned | `rejectsAlgNone`, `rejectsAlgorithmConfusion` |
| Token integrity: expiry, issuer, audience, signature | `JwtServiceTest.rejection` |
| Mismatched key pair refused at **startup** | `mismatchedPairFailsFast` |
| Refresh and one-time tokens stored **hashed** | `resetTokenIsStoredHashed`, `hashDiffersFromToken` |
| Refresh rotation with reuse detection | `detectsTokenReuse` |
| One-time tokens single use and purpose-separated | `verificationTokenIsSingleUse`, `verificationTokenCannotResetPassword` |
| Password change and reset revoke every session | `changeRevokesOtherSessions`, `resetRevokesAllSessions` |
| Account lockout; lockout cleared by a successful reset | `locksAfterRepeatedFailures`, `resetClearsLockout` |
| **Suspension cannot be bypassed** by a stale link or via Google | `oldLinkDoesNotResurrectSuspendedAccount`, `suspendedAccountIsRefused` |
| Google: unverified email refused; no password ever stored; `sub` is the key | `GoogleOAuthServiceTest` |
| Tokens in HTTP-only cookies, never in a body | `signsInAndSetsCookies` |
| CSRF protection enabled, as cookie auth requires | `SecurityConfig` |
| `/internal/**` requires a service-to-service authority | `SecurityConfig` |
| **Database isolation holds** | `DatabaseOwnershipIntegrationTest`, verified in both directions |
| Authentication audit trail | `auth_event` table |
| Secrets absent from source, including a PEM **body** | CI R9 |

### 13a.2 Still open for auth-service

| Gap | Impact | Closed in |
|---|---|---|
| No rate limiting at the service boundary | The edge limit exists in configuration; lockout is the only in-service control | 3, 11 |
| Revocation relies on the token rotation family, not a Redis deny list | Redis is not wired yet | 3 |
| No email delivery | Links are published as domain events; no transport exists | 3 |
| No Kafka publisher verified | The outbox is written; no broker was available to publish to | 3 |
| No multi-factor authentication | A password is the only factor | 11 |
| No list of a user's own active sessions | Sessions are revoked, but not displayed | 10 |

### 13a.3 How these were found

Every real vulnerability in 13a.1 was found by **running** something, not by reading it. Two
suspension bypasses and two rollback-induced security failures were invisible by inspection and
surfaced only when an integration test asserted the property. That is the argument for having
integration tests at all, and the reason the database-isolation test was verified in **both
directions** — granting a foreign `CONNECT` to confirm it fails, then revoking to confirm it
passes — rather than being accepted as green on its first successful run.

## 14. Security review checklist

Used in Phase 11 and for any change touching authentication, authorisation, uploads, payments or
secrets.

- [ ] No secret added to source, images, logs or the frontend
- [ ] No new role beyond `USER` and `ADMIN`
- [ ] Every new endpoint is deny-by-default and ownership-checked
- [ ] Every new endpoint has a test for the cross-user case
- [ ] Every new consumer is idempotent
- [ ] Every new user-supplied file path is validated by content
- [ ] Every new database access is inside the owning service
- [ ] Every new internal call has a timeout
- [ ] Every new admin action is audited
- [ ] Documentation updated in the same change
- [ ] No check weakened, skipped or made advisory
